**[문제이해 및 구상]**
- 문제의 조건이 까다롭다거나 말의 의미를 모르겠거나 하지는 않았음.
- 그러나 배열의 크기가 자꾸만 변한다는 점에서 배열을 어떻게 관리해야할지 고민스러웠음.
- 0을 채워주는 일을 구현하기에는 너무 번거로울 것 같아서 처음부터 최대 크기인 100*100 배열 선언하기로.
- 그러나 이런 방식을 했을 때의 문제점을 충분히 고려하지 않고 구현을 시작해버림.
- 문제는 명확했으나 헷갈렸던 것은 출현 빈도와 숫자 순으로 정렬시키지만 넣을 때는 숫자, 출현빈도 순이라서.
- 그리고 행에 대한 정렬 수행/열에 대한 정렬 수행이 반복적으로 바뀌는 것도 계속 헷갈렸음.
- 숫자와 출현빈도를 담는 것은 딕셔너리로 관리하고 그것을 리스트에 넣어 sort하기로 구상.

**[구현+디버깅]**
- 구현에서 문제를 겪었음.
- 한 배열을 계속적으로 쓰는 것이다 보니 전 애들의 흔적을 지우는 과정이 필요하다는 것을 구현 중 깨달음.
- 심지어 이것도 오픈테케부터 틀려서 배열을 초마다 다 찍어보다가 깨달음.
- 전 애들을 지울 때 index가 헷갈려서 몇 번을 돌려보고 확인했는지 모르겠음.
- 지금 생각해보니 그냥 배열을 새로 선언을 하거나 미리 최대row*최대col을 순회하며 0으로 만드는 편이 편했을듯.
- 딱 지워야 하는 애들을 찾아서 지우는 과정을 구현하다보니 실수가 계속 생겼고 그 버그를 잡느라 시간을 다 씀.

**[문제 1차 제출 -> 실패]**
- 엣지케이스에서 걸림.
- 시작하자마자 처리하기와 같은 엣지케이스는 스터디 때도 과정평가 때도 몇 번을 경험했던 케이스인데
- 구현을 다 했다는 기쁨과 시간이 얼마 남지 않아 조급하다는 이유로 문제를 검증없이 제출해버림.

2차 제출 때 성공.

**[잘한 점]**
- 적절한 함수화?
- 디버깅을 위해 배열을 print하는 함수를 구현한 것. 덕분에 디버깅 편했음.

**[못한 점]**
- 이렇게까지 구현이 오래 걸릴 문제였나싶음.
- 메모리가 터질까봐 100*100 배열을 계속 내용물 바꿔가며 쓰는 방법을 썼지만
- 되려 index 계산하다가 덤벙덤벙 실수만 계속함.
- index 실수를 하도 많이 하니까 index 계산할 일만 있으면 기가 죽음.
- 디버깅도 너무 오래 걸렸음. 충분히 검증할 시간이 없었음.
- 구상 시간이 20분을 넘어가기 시작하니까 구현 및 디버깅 시간이 부족할까봐 마음이 조급해짐.
- 그렇다고 구상을 짧게 하자니 구현이 오래 걸리는 것 같음. 적절한 밸런스는 뭘까.
- 자주 본 엣지 케이스임에도 충분히 고려하지 못하고 제출해버린 점.
