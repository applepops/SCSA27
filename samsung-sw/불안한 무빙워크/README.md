# [불안한 무빙워크](https://www.codetree.ai/frequent-problems/samsung-sw/problems/unstable-moving-walk)

**SW 역량 테스트** › 2020 하반기 오전 1번 문제

개인코드리뷰 <br/>
260820 불안한무빙워크

코드길이: 주석 포함 80줄 <br/>
메모리: 19MB <br/>
수행시간: 131ms

14:35 ~ 14: 55 문제이해 및 구상 <br/>
14:55 ~ 15: 25 구현 <br/>
15:25 ~ 15: 32 오픈 테케 돌려봄 -> 성공 <br/>
15:33 1차 제출 -> 실패 <br/>
15:33 ~ 15:38 1차 디버깅(5분) <br/>
15: 38 2차 제출 -> 성공

**[문제이해 및 구상]**
- 또 시뮬레이션 문제구나 싶었음.
- 처음부터 구상하려고 하지 않고 문제를 완전히 이해할 때까지 구상하지 않으려 노력함.
- 무빙워크는 큐로 관리하는 것이 베스트라고 느껴 선택하고 안에 같이 넣어서 관리할 값들 생각함.
- 대략적인 코드 흐름을 그림으로 그려넣고 조건들 번호 매겨가며 꼼꼼하게 구상함.

**[구현]**
- 구상한 그대로 구현을 해서 어려움이 없었음.
- 그런데 처음에 큐에 튜플로 집어넣었다가 index로 튜플 안의 값들 꺼낼 때 오류가 나서 당황함.
- 그래서 바로 리스트로 바꿨음. 왜 안된거지? -> 값을 변경하려고 해서 그런 거였음. 사용 의도를 생각하고 선택하자.
- 구현 다 하고 오픈 테케 일일이 찍어보면서 문제에서 준 그림이랑 완전히 일치하는지 확인함.
- 뭔가 느낌이 좋아서 바로 제출해버림. 그런데 시간초과가 나서 슬퍼짐.

**[1차 디버깅]**
- 시간초과의 원인을 생각해보았을 때 내 알고리즘 자체의 시간복잡도가 무거워서는 아닌 것 같았고
- 직감적으로 while이 무한루프를 돌았겠거니하는 느낌이 와서 버그를 잡기 용이했음.
- K가 최댓값(2N)개일 때를 시험 삼아 그제서야 돌려봤는데 끝나지 않아서 종료조건이 잘못되었음을 깨달았고
- 상대적으로 손쉽게 버그를 잡기는 했음.

성공.

**[잘한 점]**
- 구상 후에 문제 재정독하면서 빠뜨린 부분 없나 보고 구현 후에도 한 번 더 봄.
- 이렇게 하니까 '1번부터 3번까지의 과정 중 언제든 N번에 사람이 있으면 내리게 한다'는 말을 발견하여 실수 예방함.
- 또 K '이상'일 때를 발견해서 실수 예방함.
- 두 가지의 실수를 미리 발견했다는 점에서 기쁨.
- 오늘은 조건을 놓쳐서 틀리는 일은 없었음.


**[못한 점]**
- 오픈 테케만 step-by-step으로 병적으로 찍어내며 확인해놓고
- 당연히 기본적으로 깔고 들어가야 하는 양극단 값 확인 test case를 돌려보지 않아서
- 한 번에 성공하지 못했다는 것이 매우 아쉬움.
- 왠지 느낌이 좋아서 더 검증하지 않고 제출해버리는 미련한 짓을 했다. 평소처럼 하자.
- 전체가 2N개라는 것을 망각하고 N개만 확인한 것이 시간 초과의 원인.
- 시험 때는 이게 시간 초과인 것도 모를 텐데 앞으로 양극단 test case는 무조건 돌려보고 제출할 것.


[특이사항]
- 구현하던 중에 갑자기 공포스러워져서 심호흡을 했다.
- 몇 번 심호흡하고 눈 감고 있으니 좀 나아졌다.
- 멘탈관리를 할 필요가 있을 것 같다.
